# 코드베이스 설계

**깊은 모듈**을 설계한다: 작은 인터페이스 뒤에 많은 동작을 두고, 깔끔한 시임에 배치하며, 그 인터페이스를 통해 테스트할 수 있게 한다. 코드를 설계하거나 재구성하는 곳이라면 어디서든 이 용어와 원칙을 사용한다. 목표는 호출자에게는 레버리지, 유지보수자에게는 지역성, 모두에게는 테스트 용이성이다.

## 용어집

다음 용어를 정확히 사용한다. "component", "service", "API", "boundary"로 바꿔 부르지 않는다. 일관된 언어가 핵심이다.

**모듈(Module)**: 인터페이스와 구현을 가진 모든 것. 의도적으로 규모를 가리지 않는다: 함수, 클래스, 패키지, 여러 계층을 가로지르는 슬라이스 모두 해당한다. _피할 말_: unit, component, service.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 사용하기 위해 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변식, 순서 제약, 오류 모드, 필수 설정, 성능 특성까지 포함한다. _피할 말_: API, signature (너무 좁다. 타입 수준의 표면만 가리킨다).

**구현(Implementation)**: 모듈 내부, 즉 코드 본문. **어댑터**와 구별된다. 어떤 것은 작은 어댑터이면서 큰 구현일 수도 있고(Postgres 리포지터리), 큰 어댑터이면서 작은 구현일 수도 있다(인메모리 가짜 객체). 시임이 주제일 때는 "어댑터"를, 그 외에는 "구현"을 쓴다.

**깊이(Depth)**: 인터페이스에서의 레버리지. 호출자(또는 테스트)가 배워야 하는 인터페이스 한 단위당 실행해 볼 수 있는 동작의 양. 작은 인터페이스 뒤에 많은 동작이 있으면 **깊고**, 인터페이스가 구현만큼 복잡하면 **얕다**.

**시임(Seam)** _(Michael Feathers)_: 그 자리를 수정하지 않고도 동작을 바꿀 수 있는 곳. 모듈의 인터페이스가 놓이는 *위치*. 시임을 어디에 둘지는 그 뒤에 무엇을 둘지와는 별개의 설계 결정이다. _피할 말_: boundary (DDD의 bounded context와 의미가 겹친다).

**어댑터(Adapter)**: 시임에서 인터페이스를 충족하는 구체적인 것. 실체(안에 무엇이 있는가)가 아니라 *역할*(어떤 자리를 채우는가)을 나타낸다.

**레버리지(Leverage)**: 호출자가 깊이로부터 얻는 것. 배우는 인터페이스 한 단위당 더 많은 능력. 하나의 구현이 N개의 호출 지점과 M개의 테스트에 걸쳐 보답한다.

**지역성(Locality)**: 유지보수자가 깊이로부터 얻는 것. 변경, 버그, 지식, 검증이 호출자들에 흩어지지 않고 한곳에 모인다. 한 번 고치면 모든 곳이 고쳐진다.

## 깊음 vs 얕음

**깊은 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│   Small Interface   │  ← 적은 메서드, 단순한 매개변수
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 복잡한 로직이 숨겨짐
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현 (피할 것):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 많은 메서드, 복잡한 매개변수
├─────────────────────────────────┤
│  Thin Implementation            │  ← 그냥 통과시키기만 함
└─────────────────────────────────┘
```

인터페이스를 설계할 때 묻는다:

- 메서드 수를 줄일 수 있는가?
- 매개변수를 단순화할 수 있는가?
- 더 많은 복잡성을 안에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성이다.** 깊은 모듈도 내부적으로는 작고, 모킹 가능하고, 교체 가능한 부품들로 이루어질 수 있다. 그것들이 인터페이스의 일부가 아닐 뿐이다. 모듈은 인터페이스의 **외부 시임**뿐 아니라 **내부 시임**(구현에 비공개이며 자체 테스트가 사용하는)도 가질 수 있다.
- **삭제 테스트.** 모듈을 삭제한다고 상상해 본다. 복잡성이 사라진다면 그저 통과시키는 모듈이었다. 복잡성이 N개의 호출자에 다시 나타난다면 제 몫을 하고 있던 것이다.
- **인터페이스가 곧 테스트 표면이다.** 호출자와 테스트는 같은 시임을 건넌다. 인터페이스 *너머*를 테스트하고 싶다면 모듈의 형태가 잘못되었을 가능성이 크다.
- **어댑터가 하나면 가설상의 시임이다. 둘이면 진짜 시임이다.** 그 시임을 가로질러 실제로 무언가가 달라지지 않는 한 시임을 도입하지 않는다.

## 테스트 용이성을 위한 설계

좋은 인터페이스는 테스트를 자연스럽게 만든다:

1. **의존성을 만들지 말고 받아들인다.**

   ```typescript
   // 테스트하기 쉬움
   function processOrder(order, paymentGateway) {}

   // 테스트하기 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 일으키지 말고 결과를 반환한다.**

   ```typescript
   // 테스트하기 쉬움
   function calculateDiscount(cart): Discount {}

   // 테스트하기 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **작은 표면적.** 메서드가 적을수록 필요한 테스트도 적다. 매개변수가 적을수록 테스트 준비가 단순하다.

## 관계

- **모듈**은 정확히 하나의 **인터페이스**(호출자와 테스트에게 보이는 표면)를 가진다.
- **깊이**는 **모듈**의 속성이며, 그 **인터페이스**를 기준으로 측정한다.
- **시임**은 **모듈**의 **인터페이스**가 놓이는 곳이다.
- **어댑터**는 **시임**에 위치하며 **인터페이스**를 충족한다.
- **깊이**는 호출자에게 **레버리지**를, 유지보수자에게 **지역성**을 만들어 준다.

## 채택하지 않은 관점

- **구현 줄 수 대비 인터페이스 줄 수의 비율로서의 깊이** (Ousterhout): 구현을 부풀리는 것을 보상한다. 우리는 레버리지로서의 깊이를 사용한다.
- **TypeScript의 `interface` 키워드나 클래스의 public 메서드로서의 "인터페이스"**: 너무 좁다. 여기서 인터페이스는 호출자가 알아야 하는 모든 사실을 포함한다.
- **"Boundary"**: DDD의 bounded context와 의미가 겹친다. **시임** 또는 **인터페이스**라고 한다.
