# 로그인 spec

Status: ready-for-agent

## 문제 정의

이 서비스에는 아직 "누가 쓰고 있는지" 확인하는 방법이 없다. 그래서 사용자마다 다른 화면을 보여 주거나, 남이 내 정보를 보지 못하게 막을 수 없다.

로그인을 만들 때는 두 가지가 동시에 필요하다.

- **빨라야 한다.** 화면을 누를 때마다 서버가 명부를 뒤져 "이 사람 누구지?"를 확인하면 느려진다.
- **도둑맞아도 피해가 작아야 한다.** 누군가 내 로그인 정보를 몰래 복사해 가더라도, 오래 쓰지 못하고 곧 들통나야 한다.

## 해결책

학교 출입에 비유하면 이렇다.

- 사용자는 이메일과 비밀번호로 **로그인**한다. 그러면 15분짜리 출입증(**Access Token**)과, 출입증을 다시 받을 때 쓰는 교환권(**Refresh Token**)을 받는다.
- 경비원(서버)은 출입증에 찍힌 위조 방지 도장만 보고 통과시킨다. 명부를 찾아보지 않으니 빠르다.
- 출입증이 만료되면 교환권을 내고 새 출입증과 **새** 교환권을 받는다(**토큰 교환**). 낸 교환권은 그 자리에서 버려진다.
- 이미 버려진 교환권을 누가 다시 내밀면, 복사된 것으로 보고 그 로그인(**세션**)을 바로 끊는다(**재사용 감지**). 다만 탭 여러 개가 동시에 같은 교환권을 내는 정상적인 경우를 위해, 교환 직후 10초 동안은 봐준다(**유예 시간**).
- 30분 동안 교환이 없으면 세션은 저절로 끝난다(**세션 만료**).
- 비밀번호를 15분 안에 5번 틀리면, 그 이메일로는 15분 동안 로그인할 수 없다(**로그인 차단**).

서버가 기억하는 것은 세션(교환권의 줄)뿐이다. 출입증은 서버가 기억하지 않는다. 이 결정의 이유는 ADR-0001에 있다.

## 사용자 스토리

1. 사용자로서, 나는 이메일과 비밀번호로 로그인하고 싶다. 그래야 내 계정으로 서비스를 쓸 수 있다
2. 사용자로서, 나는 로그인한 뒤 화면을 누를 때마다 다시 로그인하지 않고 싶다. 그래야 편하게 쓸 수 있다
3. 사용자로서, 나는 로그인한 뒤의 요청이 빠르게 처리되기를 원한다. 그래야 화면이 답답하지 않다
4. 사용자로서, 나는 15분이 지나 Access Token이 만료되어도 눈치채지 못한 채 계속 쓰고 싶다. 그래야 작업이 끊기지 않는다
5. 사용자로서, 나는 새로고침해도 로그인이 유지되기를 원한다. 그래야 새로고침할 때마다 다시 로그인하지 않는다
6. 사용자로서, 나는 링크를 새 탭으로 열어도 로그인이 유지되기를 원한다. 그래야 여러 화면을 동시에 볼 수 있다
7. 사용자로서, 나는 브라우저를 다시 켜서 탭 여러 개가 한꺼번에 복원되어도 로그아웃되지 않기를 원한다. 그래야 하던 일을 바로 이어 갈 수 있다
8. 사용자로서, 나는 휴대폰 브라우저와 노트북에서 동시에 로그인해 있고 싶다. 그래야 기기를 바꿔 가며 쓸 수 있다
9. 사용자로서, 나는 30분 넘게 자리를 비우면 자동으로 로그아웃되기를 원한다. 그래야 공용 컴퓨터에 로그인을 두고 가도 남이 쓰지 못한다
10. 사용자로서, 나는 계속 쓰고 있는 동안에는 로그아웃되지 않기를 원한다. 그래야 긴 작업을 하다가 쫓겨나지 않는다
11. 사용자로서, 나는 로그아웃 버튼을 누르면 이 브라우저의 로그인이 끝나기를 원한다. 그래야 내가 원할 때 로그인을 끝낼 수 있다
12. 사용자로서, 나는 한 기기에서 로그아웃해도 다른 기기의 로그인은 유지되기를 원한다. 그래야 노트북에서 로그아웃할 때 휴대폰까지 다시 로그인하지 않는다
13. 사용자로서, 나는 로그아웃한 뒤 새로고침해도 로그인 상태로 돌아가지 않기를 원한다. 그래야 로그아웃이 확실히 됐다고 믿을 수 있다
14. 사용자로서, 나는 이메일이나 비밀번호를 틀리면 무엇이 틀렸는지 알려 주는 대신 "이메일 또는 비밀번호가 올바르지 않습니다"라는 안내를 받고 싶다. 그래야 남이 내 이메일의 가입 여부를 알아낼 수 없다
15. 사용자로서, 나는 비밀번호를 여러 번 틀려 로그인 차단이 되면 그 사실과 "잠시 후 다시 시도"하라는 안내를 받고 싶다. 그래야 왜 로그인이 안 되는지 안다
16. 사용자로서, 나는 누군가 내 이메일로 비밀번호를 계속 찍어 볼 때 막히기를 원한다. 그래야 내 계정이 안전하다
17. 사용자로서, 나는 로그인 차단이 15분 뒤 저절로 풀리기를 원한다. 그래야 따로 문의하지 않아도 다시 로그인할 수 있다
18. 사용자로서, 나는 로그인에 성공하면 그동안 틀린 횟수가 지워지기를 원한다. 그래야 나중에 한두 번 틀렸다고 바로 차단되지 않는다
19. 사용자로서, 나는 내 Refresh Token이 복사되어 쓰이면 그 세션이 바로 끊기기를 원한다. 그래야 도둑이 내 계정을 오래 쓰지 못한다
20. 사용자로서, 나는 재사용 감지로 세션이 끊기면 로그인 화면으로 안내되기를 원한다. 그래야 다시 로그인해서 계속 쓸 수 있다
21. 사용자로서, 나는 내 로그인 정보가 웹페이지의 스크립트로 읽히지 않는 곳에 보관되기를 원한다. 그래야 악성 스크립트가 끼어들어도 Refresh Token을 훔쳐 가기 어렵다
22. 사용자로서, 나는 서버의 Redis가 잠시 멈춰도 이미 열어 둔 화면은 계속 쓰고 싶다. 그래야 작은 장애로 작업이 바로 끊기지 않는다
23. 사용자로서, 나는 Redis가 멈춰 로그인할 수 없을 때 "잠시 후 다시 시도"라는 안내를 받고 싶다. 그래야 내 비밀번호가 틀린 것으로 오해하지 않는다
24. 사용자로서, 나는 와이파이가 잠깐 끊겨 토큰 교환 요청을 다시 보내도 로그아웃되지 않기를 원한다(10초 안이라면). 그래야 불안정한 네트워크에서도 쓸 수 있다
25. 개발자로서, 나는 Access Token이 위조되었거나 만료되었으면 서버가 요청을 거절하기를 원한다. 그래야 보호된 기능을 안심하고 만들 수 있다
26. 개발자로서, 나는 보호된 요청을 처리할 때 "지금 요청한 사용자가 누구인지"를 바로 알고 싶다. 그래야 사용자별 기능을 만들 수 있다
27. 운영자로서, 나는 JWT 서명용 비밀 키를 코드가 아니라 서버 실행 환경에서 넣고 싶다. 그래야 키가 저장소에 노출되지 않는다

## 구현 결정

### 전체 구조

- 화면은 React(TypeScript), 서버는 Spring Boot, 사용자 정보는 PostgreSQL, 세션과 로그인 차단 기록은 Redis에 둔다.
- 화면과 서버는 같은 사이트에서 서비스한다. 개발 중에는 React 개발 서버의 프록시로 같은 주소처럼 맞춘다.
- Access Token은 stateless로 서명만 확인하고, 세션만 Redis에 저장한다 (ADR-0001). 보호된 요청을 처리할 때 서버는 Redis를 조회하지 않는다.
- 이 spec은 사용자 정보를 **읽기만** 한다. 사용자 정보에는 식별자, 이메일(중복 없음), bcrypt로 바꾼 비밀번호가 있다고 가정한다. 사용자를 만드는 일은 회원가입 spec의 몫이다.

### 서버 모듈

- **인증 모듈**: 로그인, 토큰 교환, 로그아웃 세 가지 동작을 가진 깊은 모듈. 아래의 세션 저장소, 로그인 차단 기록, Access Token 발급·검증을 안에 숨긴다.
- **세션 저장소** (Redis): 세션을 만들고, 교환하고, 폐기한다.
- **로그인 차단 기록** (Redis): 이메일별 실패 횟수를 센다.
- **Access Token 발급·검증**: HS256 서명. 보호된 요청의 검증은 Spring Security가 맡는다.
- **시계**: 서버가 지금 시각을 아는 곳. 테스트에서 바꿔 끼워 시간을 앞당길 수 있어야 한다. 15분, 30분, 10초는 모두 이 시계로 계산한다.

### HTTP API 계약

| 동작 | 요청 | 성공 응답 | 실패 응답 |
|---|---|---|---|
| 로그인 | `POST /api/auth/login`, 본문에 이메일과 비밀번호 | 200, 본문에 Access Token, Refresh Token 쿠키 설정 | 401 공통 메시지 / 429 로그인 차단 안내 / 503 잠시 후 다시 시도 |
| 토큰 교환 | `POST /api/auth/refresh`, Refresh Token 쿠키 | 200, 본문에 새 Access Token, 새 Refresh Token 쿠키 설정 | 401 + 쿠키 삭제 (만료, 재사용 감지, 알 수 없는 토큰) / 503 잠시 후 다시 시도 |
| 로그아웃 | `POST /api/auth/logout`, Refresh Token 쿠키 | 항상 성공, 쿠키 삭제 | 없음 |
| 보호된 요청 | `Authorization: Bearer <Access Token>` | 요청한 사용자의 식별자를 알 수 있음 | 401 (서명 불일치, 만료, 없음) |

- 로그인 실패 메시지는 이메일이 없을 때와 비밀번호가 틀렸을 때 **글자 하나까지 같다**. 응답 시간 차이로 가입 여부를 알아내지 못하도록, 이메일이 없을 때도 가짜 bcrypt 값으로 비밀번호 대조를 한 번 수행한다.

### Access Token

- 유효 기간 15분. 서명 방식 HS256.
- 담는 내용은 사용자 식별자, 발급 시각, 만료 시각뿐이다. 권한 정보는 담지 않는다.
- 서명용 비밀 키는 서버 실행 시 환경 변수로 받는다. 키가 없으면 서버가 시작되지 않는다.
- 화면은 Access Token을 메모리에만 둔다. localStorage나 쿠키에 두지 않는다.

### Refresh Token과 쿠키

- Refresh Token은 JWT가 아니라 추측할 수 없는 긴 무작위 문자열이다.
- Redis에는 Refresh Token의 원래 값이 아니라 되돌릴 수 없게 바꾼 값(해시)을 저장한다. 유일한 예외는 유예 시간용으로 10초 동안 보관하는 새 Refresh Token의 원래 값이다.
- 쿠키 설정: HttpOnly, Secure, SameSite=Strict. 경로는 `/api/auth` 아래로 제한해, 보호된 요청에는 Refresh Token이 따라가지 않게 한다.

### 세션

- 로그인할 때마다 새 세션을 하나 만든다. 한 사용자가 가질 수 있는 세션 수에는 제한이 없다.
- 세션에는 사용자 식별자, 현재 Refresh Token, 직전 Refresh Token과 그 교환 시각, 유예 시간용 새 Refresh Token(10초 보관), 그리고 이 세션에서 지금까지 발급된 Refresh Token 목록(재사용 감지용)이 연결된다.
- **세션 만료**: 마지막 토큰 교환(또는 로그인)으로부터 30분이 지나면 세션이 사라진다. 토큰 교환할 때마다 30분을 다시 센다. 최대 수명 상한은 없다.

### 토큰 교환 규칙

제출된 Refresh Token에 따라 다음과 같이 처리한다.

1. **현재 Refresh Token**이면: 새 Refresh Token과 새 Access Token을 발급한다. 제출된 토큰은 "직전 Refresh Token"이 된다.
2. **직전 Refresh Token**이고 교환 후 **10초 이내**이면 (유예 시간): 재사용 감지로 보지 않는다. 방금 발급한 **같은** Refresh Token을 다시 돌려주고, Access Token은 새로 발급한다.
3. **직전 Refresh Token인데 10초가 지났거나**, **두 단계 이전 이상의 Refresh Token**이면: 재사용 감지. **그 세션만** 폐기하고 401을 돌려준다. 같은 사용자의 다른 세션은 그대로 둔다.
4. **어느 세션에도 없는 Refresh Token**이면(만료됐거나 처음 보는 값): 401을 돌려준다.

- 한 세션에 대한 토큰 교환은 원자적으로(중간에 다른 요청이 끼어들 수 없게) 처리한다. 두 요청이 동시에 와도 1번은 정확히 한 번만 일어나야 한다.
- 탭끼리 교환 순서를 맞추지 않는다(Web Locks 등 미사용). 동시에 일어나는 교환은 유예 시간으로 흡수한다.

### 로그인 차단

- 실패 횟수는 이메일을 기준으로 센다. 이메일은 앞뒤 공백을 지우고 소문자로 바꾼 뒤 비교한다.
- 존재하지 않는 이메일도 똑같이 센다.
- 마지막 실패로부터 15분이 지나면 실패 횟수는 저절로 사라진다. 그래서 "15분 안에 5번 실패"가 차단 조건이 된다.
- 5번째 실패부터 15분 동안 로그인 차단. 차단 중에는 비밀번호를 대조하지 않고 429와 안내 메시지를 돌려준다. 맞는 비밀번호여도 마찬가지다.
- 로그인에 성공하면 그 이메일의 실패 횟수를 지운다.

### 로그아웃

- 이 브라우저의 세션만 폐기하고 Refresh Token 쿠키를 지운다.
- 세션이 이미 만료됐거나 없어도, Redis가 멈춰 있어도 성공으로 처리하고 쿠키를 지운다.
- 이미 발급된 Access Token은 만료될 때까지 유효하다 (ADR-0001). 화면은 메모리의 Access Token을 즉시 지운다.

### Redis 장애

- 로그인과 토큰 교환은 503과 "잠시 후 다시 시도" 안내로 실패한다.
- 보호된 요청은 Redis를 보지 않으므로 Access Token이 유효한 동안 계속 처리된다.

### 화면 인증 모듈

화면의 나머지 부분은 이 모듈만 통해 로그인을 다룬다. 인터페이스:

- **로그인하기**(이메일, 비밀번호): 성공하면 Access Token을 메모리에 둔다. 실패하면 서버의 안내 메시지(공통 실패, 로그인 차단, 잠시 후 다시 시도)를 구분해 돌려준다.
- **로그아웃하기**: 서버에 로그아웃을 요청하고, 결과와 상관없이 메모리의 Access Token을 지운다.
- **인증 요청 보내기**: 요청에 Access Token을 붙인다. 401을 받으면 토큰 교환을 한 번 하고 같은 요청을 한 번 다시 보낸다. 교환에 실패하면 로그아웃 상태가 된다.
- **로그인 상태 복원**: 앱이 시작될 때(새로고침, 새 탭 포함) 토큰 교환을 한 번 시도해 로그인 상태를 되살린다.
- **로그인 상태 알림**: 로그인 상태가 바뀌면 화면에 알린다. 로그아웃 상태가 되면 화면은 로그인 화면으로 안내한다.
- 한 탭 안에서 여러 요청이 동시에 401을 받으면 토큰 교환은 한 번만 한다. 탭과 탭 사이는 맞추지 않는다.

## 테스트 결정

### 좋은 테스트란

- 내부 구현이 아니라 시임에서 보이는 동작만 확인한다. 서버 테스트는 Redis를 직접 들여다보지 않고 HTTP 응답으로 확인하고, 화면 인증 모듈 테스트는 인터페이스의 결과로 확인한다.
- 기댓값은 이 spec에 적힌 숫자와 문장에서 가져온다(15분, 30분, 10초, 5번, 공통 메시지). 코드가 계산하는 방식을 테스트에서 다시 계산하지 않는다.
- 테스트 이름은 용어집의 용어로 쓴다 (예: "유예 시간이 지난 직전 Refresh Token은 재사용 감지로 세션을 폐기한다").

### 왜 테스트 층이 둘인가

E2E로는 시간 규칙(15분, 30분, 10초, 로그인 차단 15분)을 앞당겨 확인할 수 없으므로, 시간과 세부 규칙은 시계를 바꿔 끼울 수 있는 개발 테스트 층에서 확인한다.

### 1층: 인수 테스트 (E2E)

- 실제 브라우저(Playwright)로 화면, 서버, PostgreSQL, Redis를 모두 띄운 상태에서 **흐름과 연결만** 확인한다.
- 시간을 앞당기지 않는다. E2E에서 토큰 교환은 새로고침과 새 탭 열기로 일으킨다.

시나리오:

1. **로그인 → 요청**: 올바른 이메일과 비밀번호로 로그인하면, 로그인한 사용자만 볼 수 있는 화면이 보인다.
2. **새로고침해도 로그인 유지 (토큰 교환)**: 로그인 후 새로고침해도 로그인 상태로 같은 화면이 보인다.
3. **여러 탭을 동시에 열 때 유예 동작**: 로그인 후 같은 화면을 탭 5개로 동시에 열면, 모든 탭이 로그인 상태다. 그 뒤 아무 탭이나 새로고침해도 로그인 상태다.
4. **로그아웃**: 로그아웃하면 로그인 화면으로 안내된다. 새로고침해도 로그아웃 상태이고, 로그인한 사용자만 볼 수 있는 화면 주소로 직접 가도 로그인 화면으로 안내된다.
5. **로그인 실패 메시지**: 틀린 비밀번호로 로그인하면 "이메일 또는 비밀번호가 올바르지 않습니다"가 보인다. 존재하지 않는 이메일로 로그인해도 같은 메시지가 보인다.
6. **로그인 차단 메시지**: 같은 이메일로 5번 틀리면 로그인 차단 안내가 보인다. 그 상태에서 올바른 비밀번호를 넣어도 로그인 차단 안내가 보인다.

### 2층: 개발 테스트 (TDD 시임)

- **서버 HTTP API**: 로그인, 토큰 교환, 로그아웃, 보호된 요청을 실제 HTTP 요청으로 확인한다. Redis와 PostgreSQL은 테스트용으로 진짜를 띄운다(Testcontainers). 시계는 테스트용으로 바꿔 끼워 시간을 앞당긴다. Redis 장애는 테스트용 Redis를 멈춰서 만든다.
- **화면 인증 모듈**: 위 인터페이스를 가짜 서버 응답으로 확인한다.

### E2E를 쌓는 순서

- **첫 티켓**에서 E2E 뼈대(화면·서버·PostgreSQL·Redis를 띄우고 브라우저로 조작하는 환경)와 시나리오 1을 만든다.
- 이후 티켓은 자기 기능의 E2E 시나리오를 **같은 티켓 안에서** 함께 추가한다. E2E를 마지막 티켓에 몰아서 쓰지 않는다.

### 테스트 선례

저장소에 아직 테스트가 없다. 첫 티켓이 서버 HTTP API 테스트, 화면 인증 모듈 테스트, E2E의 선례가 된다.

## 범위 밖

- 회원가입 (사용자는 이미 있다고 가정)
- 소셜 로그인 (구글, 카카오 등)
- 모바일 앱 지원
- 권한 구분 (관리자/일반)
- "로그인 유지" 체크박스
- 비밀번호 찾기·변경
- "모든 기기에서 로그아웃"

- 탭끼리 토큰 교환 순서 맞추기 (Web Locks 등)
- 로그아웃 즉시 Access Token 무효화

## 추가 메모

받아들이기로 한 위험:

- 로그아웃하거나 세션이 폐기되어도, 이미 발급된 Access Token은 최대 15분 동안 쓸 수 있다 (ADR-0001).
- 세션 최대 수명 상한이 없으므로, 30분 안에 한 번씩 토큰 교환이 일어나는 한 세션은 끝나지 않는다.
- 도둑이 토큰 교환 후 10초 안에 직전 Refresh Token을 내면 유예 시간에 걸려 통과한다.
- 네트워크가 10초 넘게 끊겨 토큰 교환 응답을 받지 못하면, 다음 교환이 재사용 감지로 처리되어 로그아웃된다.
- 실제로 느끼는 "미사용 시간"은 마지막 토큰 교환을 기준으로 세므로 15분에서 30분 사이로 들쭉날쭉하다.
- 남의 이메일로 일부러 5번 틀려서 그 사람을 15분 동안 로그인 차단할 수 있다.
- Redis가 멈춘 동안 로그아웃하면 쿠키만 지워지고 세션은 30분 뒤 세션 만료로 사라진다.
