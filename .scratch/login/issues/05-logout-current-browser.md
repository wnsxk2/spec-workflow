# 05: 현재 브라우저에서 로그아웃하기

**만들 것:** 사용자가 로그아웃 버튼을 누르면 이 브라우저의 세션을 끝내고 로그인 화면으로 돌아간다. 정상적으로 로그아웃한 뒤에는 새로고침이나 보호된 화면 직접 접근으로 로그인이 복원되지 않으며, 다른 기기의 세션은 유지된다.

**Blocked by:** 02: 토큰 교환으로 새로고침 후 로그인 복원하기.

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 11~13 및 ADR-0001.

## 인수 조건

- [x] Refresh Token 쿠키로 로그아웃을 요청하면 해당 세션만 폐기하고 Refresh Token 쿠키를 삭제한다. 삭제에 사용하는 쿠키 이름·경로는 발급한 쿠키와 일치한다.
- [x] 같은 사용자가 다른 기기에서 만든 세션은 폐기하지 않는다. 다른 세션의 Refresh Token으로 토큰 교환을 계속할 수 있다.
- [x] Refresh Token이 없거나 알 수 없거나 세션이 이미 만료·폐기된 경우에도 로그아웃은 성공 응답과 쿠키 삭제를 반환한다. 반복 로그아웃도 성공한다.
- [ ] Redis가 멈춰 세션을 폐기할 수 없어도 로그아웃은 성공 응답과 쿠키 삭제를 반환한다. 이때 남은 서버 세션에는 spec의 세션 만료 규칙이 적용된다.
- [x] 화면은 화면 인증 모듈을 통해 로그아웃을 요청하고 메모리의 Access Token을 즉시 지운다. 서버 요청의 성공·실패와 관계없이 로그아웃 상태를 화면에 알려 로그인 화면으로 안내한다.
- [x] 정상 응답을 받은 로그아웃 이후 새로고침해도 로그아웃 상태다. 보호된 화면 주소로 직접 이동해도 로그인 화면으로 안내된다.
- [x] 이미 발급된 Access Token은 ADR-0001에 따라 자신의 만료 시각까지 유효하다. 로그아웃 즉시 Access Token을 무효화하거나 보호된 요청에서 세션을 조회하지 않는다.
- [x] 서버 HTTP API 테스트에서 실제 PostgreSQL·Redis로 현재 세션 폐기·쿠키 삭제, 폐기한 세션의 토큰 교환 실패, 다른 세션의 교환 성공을 확인한다. 없는·알 수 없는·만료된 토큰과 반복 요청의 성공도 확인한다.
- [x] 테스트용 Redis를 실제로 멈춰 로그아웃 성공과 쿠키 삭제를 확인한다. 별도로 로그아웃 전에 발급한 Access Token의 유효 기간이 유지되는지 확인하며, Redis 내부 값 대신 HTTP 결과로 판정한다.
- [x] 화면 인증 모듈 테스트로 서버 성공·실패·네트워크 오류 각각에서 메모리의 Access Token을 지우고 상태를 알리는 동작을 확인한다. 서버 응답을 받지 못한 경우의 쿠키 삭제까지 성공했다고 간주하지 않는다.
- [x] E2E 시나리오 4인 "로그아웃 → 로그인 화면 → 새로고침 → 보호된 화면 직접 접근"을 실제 브라우저와 실제 저장소로 통과시킨다. 각 단계에서 로그아웃 상태를 확인한다.
- [x] 테스트 이름·기댓값은 용어집과 spec을 따르고, 실행 명령·결과와 미검증 항목을 기록한다.

## Comments

### 구현 기록 (2026-10-15)

**실행한 검증과 결과**

| 검증 | 명령 | 결과 |
|---|---|---|
| 서버 HTTP API 테스트 | `cd server && ./gradlew test` | 41개 통과. 이 티켓에서 더한 것: "로그아웃" 7개, Redis 장애 시 로그아웃 1개 |
| 화면 인증 모듈 테스트 | `cd web && npm test` | 26개 통과. 이 티켓에서 더한 것: "로그아웃하기" 4개 |
| 화면 타입 검사·린트·빌드 | `npm run typecheck`, `npx oxlint`, `npm run build` | 오류 없음 |
| E2E 시나리오 1~5 | `cd e2e && npm test` (Chromium, Docker Compose의 PostgreSQL·Redis) | 5개 통과. 시나리오 4는 로그아웃 버튼을 만들기 전에 실패하는 것을 먼저 확인 |

서버 테스트로 확인한 것:
- 로그아웃하면 204와 함께 발급 때와 같은 이름·경로(`refresh_token`, `/api/auth`)의 쿠키를 지우고, 그 Refresh Token으로는 토큰 교환할 수 없다
- 같은 사용자의 다른 기기 세션은 계속 토큰 교환할 수 있다
- Refresh Token이 없거나, 알 수 없거나, 세션 만료 뒤이거나, 반복 로그아웃이어도 204와 쿠키 삭제
- 로그아웃 전에 발급한 Access Token은 발급 14분 59초까지 유효하고 15분에 거절 (ADR-0001)
- 테스트용 Redis를 일시 정지해도 로그아웃은 204와 쿠키 삭제

화면 인증 모듈 테스트로 확인한 것:
- 서버 응답을 기다리기 전에 메모리의 Access Token을 지우고, 정상 응답이면 결과는 성공
- 서버 실패 응답·연결 실패여도 Access Token을 지우고 로그아웃 상태를 알리되, 결과는 실패(쿠키 삭제를 확인하지 못함)이고 안내를 싣는다
- 로그아웃하는 동안 진행 중이던 토큰 교환이 늦게 끝나도 로그인 상태로 되돌아가지 않는다 (보호 장치를 빼면 실패하는 것을 확인)

E2E 시나리오 4: 로그인 → 로그아웃 버튼 → 서버의 204 응답을 기다림 → 로그인 화면, Refresh Token 쿠키 없음 → 새로고침해도 로그인 화면 → 첫 화면 주소(`/`)로 다시 이동해도 로그인 화면. 이 앱은 주소가 하나라서, 로그인했을 때 `/`에 로그인한 사용자만 볼 수 있는 화면이 보인다.

**미검증**

- Redis가 멈춘 동안 로그아웃해서 남은 서버 세션이 세션 만료(30분)로 사라지는 것: 로그아웃이 204와 쿠키 삭제를 돌려주는 것까지만 확인했다. 남은 세션의 만료는 02의 세션 만료 규칙(서버 시계와 Redis 보관 시간)에 기대며, 이 상황을 이어서 확인하는 테스트는 없다.

**이 티켓에서 spec보다 먼저 정한 것**

- 로그아웃 성공 응답은 본문 없는 204로 한다.
- 화면에서 로그아웃의 서버 응답이 실패(2xx가 아님)이거나 서버에 닿지 못하면, 로그인 화면에 "서버에 로그아웃을 알리지 못했습니다. 새로고침하면 다시 로그인될 수 있습니다"를 보여 준다. 쿠키가 남아 있을 수 있음을 사용자에게 알리기 위해서다.
- 로그아웃하는 동안 진행 중이던 토큰 교환이 늦게 끝나면 그 결과를 버린다. 로그아웃한 화면이 다시 로그인 상태로 돌아가지 않게 하기 위해서다.
- 이미 토큰 교환에 쓴 이전 Refresh Token으로 로그아웃을 요청해도 그 Refresh Token이 속한 세션을 폐기한다. 여러 탭이 거의 동시에 교환과 로그아웃을 할 때도 세션이 남지 않게 하기 위해서다.
