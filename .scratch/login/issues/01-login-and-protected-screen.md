# 01: 로그인하고 보호된 화면 보기

**만들 것:** 개발자가 문서에 따라 로컬 개발환경을 준비하고, 사용자가 이메일과 비밀번호로 로그인해 자신만 볼 수 있는 보호된 화면을 사용한다. 개발환경 구성부터 실제 브라우저 검증까지 재현할 수 있어야 이 티켓이 완료된다.

**Blocked by:** 없음 (바로 시작 가능).

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 1~3, 8, 14, 21~23, 25~27 및 ADR-0001.

## 인수 조건: 개발환경 구축

- [x] React(TypeScript) 화면과 Spring Boot 서버를 실행할 수 있다. Node.js, 패키지 관리자, JDK, 서버 빌드 도구, Docker 및 Docker Compose(여러 컨테이너 서비스를 하나의 구성으로 실행하는 도구)의 사용 버전과 설치 전제를 문서화한다.
- [x] 로컬 PostgreSQL과 Redis를 각각 Docker Compose 서비스로 정의하고 함께 실행할 수 있다. 두 저장소를 개발자 컴퓨터에 별도로 설치하지 않아도 개발환경을 준비할 수 있으며, 컨테이너 이미지 버전을 명시해 실행 환경을 재현할 수 있다.
- [x] Docker Compose 서비스의 포트와 연결 설정을 실행 환경으로 주입하고, Spring Boot에서 접속할 주소·포트와 환경 변수의 용도를 문서화한다. 각 서비스에 healthcheck(요청을 받을 준비가 되었는지 확인하는 검사)를 구성해 실행 준비 상태를 확인할 수 있다.
- [x] PostgreSQL의 개발 데이터는 Docker 볼륨(컨테이너를 다시 만들어도 데이터를 보관하는 저장 공간)에 유지한다. 일반적인 중지·재시작과 데이터를 지우는 초기화 절차를 구분하고, PostgreSQL·Redis의 시작·중지·상태 확인·로그 확인에 사용할 Docker Compose 명령을 문서화한다.
- [x] 개발·테스트에서 사용할 최소 사용자 스키마와 테스트 데이터를 준비한다. 사용자 식별자, 중복 없는 이메일, bcrypt(비밀번호를 되돌릴 수 없는 값으로 바꾸는 방식)로 처리한 비밀번호가 있으며, 데이터 준비·초기화 방법이 재현 가능하다. 로그인 기능은 이 사용자 정보를 읽기만 한다.
- [x] React 개발 서버의 프록시(화면의 서버 요청을 Spring Boot로 전달하는 연결)를 구성한다. 실제 브라우저에서 같은 사이트로 요청하며, spec의 Secure·SameSite=Strict 쿠키 설정을 유지한 채 로그인 쿠키를 저장할 수 있다.
- [x] 데이터베이스·Redis 연결과 서명용 비밀 키를 실행 환경으로 주입한다. 필요한 환경 변수의 이름·용도와 실제 비밀값이 없는 설정 예시를 제공하고, 비밀 키가 없으면 서버가 시작되지 않는다.
- [x] 처음 저장소를 받은 개발자가 의존성 설치, 저장소 실행, 데이터 준비, 화면·서버 실행, 각 테스트 실행, 서비스 중지를 순서대로 따라 할 수 있도록 명령과 정상 동작 확인 방법을 문서화한다. 개발·테스트 데이터를 구분해 테스트 초기화가 개발 데이터를 지우지 않게 한다.
- [x] 서버 HTTP API 테스트 환경을 만든다. Testcontainers(테스트용 실제 저장소를 격리해 실행하는 도구)로 PostgreSQL·Redis를 띄우고, 실제 HTTP 요청으로 결과를 확인하며, 장애 검증을 위해 테스트용 Redis를 멈출 수 있다.
- [x] 서버의 시계(현재 시각을 제공하는 경계)를 테스트에서 바꿔 끼울 수 있다. Access Token의 15분, 이후 티켓의 세션 만료 30분·유예 시간 10초·로그인 차단 15분을 실제로 기다리지 않고 검증할 수 있는 기반을 제공한다.
- [x] 화면 인증 모듈을 가짜 서버 응답으로 검증하는 테스트 환경과, Playwright(실제 브라우저를 조작하는 테스트 도구)로 화면·서버·PostgreSQL·Redis를 함께 검증하는 E2E 환경을 만든다. E2E에서는 시간을 앞당기지 않는다.

## 인수 조건: 로그인과 보호된 요청

- [x] 올바른 이메일과 비밀번호로 로그인하면 HTTP 200, 본문에 Access Token(보호된 요청에 사용하는 수명이 짧은 증명), 쿠키에 Refresh Token(토큰 교환에 사용하는 값)을 받는다. 화면에서 보호된 요청을 보내고 로그인한 사용자의 식별자를 확인할 수 있다.
- [ ] 로그인할 때마다 Redis에 새 세션(한 번의 로그인으로 시작되는 서버 측 기록)을 만든다. 로그인 시점부터 30분의 세션 만료 기준을 두며, 한 사용자가 여러 기기에서 로그인해도 기존 세션을 덮어쓰거나 세션 수를 제한하지 않는다.
- [x] Access Token은 HS256(공유 비밀 키로 서명하는 방식)으로 서명하고, 사용자 식별자·발급 시각·만료 시각만 담으며 유효 기간은 15분이다. 권한 정보는 담지 않는다.
- [x] Spring Security가 보호된 요청의 Bearer 방식 Access Token을 검증한다. 토큰이 없거나 서명이 다르거나 만료되면 HTTP 401을 반환하고, 유효하면 요청한 사용자의 식별자를 제공한다. 보호된 요청에서는 세션이나 Redis를 조회하지 않는다.
- [x] Refresh Token은 추측할 수 없는 긴 무작위 문자열이며 JWT 형식을 사용하지 않는다. Redis에는 원래 값 대신 해시(원래 값으로 되돌릴 수 없는 값)를 저장한다. 유예 시간용 원래 값의 제한적 보관은 04에서 추가한다.
- [x] Refresh Token 쿠키는 HttpOnly(화면 스크립트로 읽지 못함), Secure(안전한 연결에 사용), SameSite=Strict(다른 사이트에서 보내는 요청에 제한)를 적용한다. 쿠키 경로는 spec이 정한 인증 API 영역으로 제한해 보호된 요청에는 Refresh Token이 따라가지 않는다.
- [x] 화면은 Access Token을 메모리에만 두고 localStorage나 쿠키에 저장하지 않는다. 화면 인증 모듈을 통해 로그인과 보호된 요청을 수행하고 로그인 상태 변화를 화면에 알린다. 세션 저장 방식과 토큰 발급·검증의 내부 처리는 서버 인증 모듈 안에 숨긴다.
- [x] 없는 이메일과 틀린 비밀번호는 모두 HTTP 401과 정확히 "이메일 또는 비밀번호가 올바르지 않습니다"를 반환하고, 화면에도 같은 메시지를 표시한다. 없는 이메일에도 가짜 bcrypt 값으로 비밀번호 대조를 한 번 수행한다.
- [x] Redis가 멈추면 로그인은 HTTP 503과 "잠시 후 다시 시도" 안내로 실패한다. 화면은 이를 비밀번호 오류와 구분해 표시한다. 이미 발급된 Access Token을 사용하는 보호된 요청은 토큰이 유효한 동안 계속 성공한다.

## 인수 조건: 검증

- [x] 문서의 절차대로 Docker Compose로 PostgreSQL·Redis를 시작해 두 서비스의 준비 상태와 Spring Boot의 실제 연결을 확인한다. 중지·재시작 후 PostgreSQL의 개발 데이터가 유지되는지 확인하고, 이 환경에서 로그인 E2E까지 실행한다.
- [x] 서버 HTTP API 테스트로 로그인 성공·공통 실패 메시지·쿠키 속성·사용자 식별자 전달·여러 세션 발급을 확인한다. 테스트용 시계로 Access Token의 15분 만료를 확인하고, 토큰 없음·서명 불일치도 검증한다.
- [x] 테스트용 Redis를 실제로 멈춰 로그인 503과 유효한 Access Token의 보호된 요청 성공을 확인한다. 비밀 키 누락에 따른 서버 시작 실패도 검증한다.
- [x] 화면 인증 모듈 테스트로 로그인 결과, 공통 실패와 일시 장애 안내의 구분, Access Token을 붙인 요청, 로그인 상태 알림을 확인한다.
- [x] E2E 시나리오 1인 "로그인 → 보호된 화면"과 시나리오 5인 "없는 이메일·틀린 비밀번호의 동일한 안내"를 실제 브라우저와 실제 저장소로 통과시킨다. 환경 실행만으로 완료 처리하지 않는다.
- [x] 테스트는 공개된 HTTP 응답·쿠키와 화면 인증 모듈의 결과를 확인한다. Redis 내부 값을 직접 읽어 통과 여부를 판단하지 않으며, 테스트 이름은 용어집의 용어를 따른다. 실행 명령·결과를 기록하고, 실행하지 못한 검증은 미검증으로 구분한다.

## 범위 경계

개발·테스트용 사용자 데이터 준비까지 포함한다. 사용자 생성 기능, 운영 서버 구축, 도메인 설정과 배포 자동화는 포함하지 않는다. 토큰 교환·로그인 복원은 02, 요청 중 자동 복구는 03, 유예 시간·재사용 감지는 04, 로그아웃은 05, 로그인 차단은 06에서 완성한다.

**미검증**

- 세션 만료 30분: 세션에 만료 시각을 기록하지만, 만료를 확인하는 토큰 교환이 아직 없어 HTTP로 확인하지 못했다. 02에서 검증한다.
- 여러 기기 로그인 때 기존 세션을 덮어쓰지 않음: 로그인마다 다른 Refresh Token을 받고 두 Access Token이 모두 통과하는 것까지만 확인했다. Access Token은 세션을 조회하지 않으므로, 세션이 각각 남아 있는지는 토큰 교환이 생기는 02에서 검증한다.
- Redis 장애는 테스트용 Redis 컨테이너를 일시 정지해 만들었다(응답이 오지 않는 장애). 연결이 거부되는 장애는 자동 테스트로 확인하지 않았다.
- 없는 이메일일 때의 가짜 bcrypt 대조는 코드로만 확인했다. 응답 시간 차이는 측정하지 않았다.
- 개발 서버(5173)를 사람이 브라우저로 직접 써 보는 확인은 하지 않았다. 같은 프록시 구성을 E2E(15173)에서 확인했다.

**이 티켓에서 spec보다 먼저 정한 것**

- 이메일 정규화(앞뒤 공백 제거·소문자)를 사용자 조회에도 적용했다. 06 인수 조건과 같은 규칙이다.
- 화면 인증 모듈은 429를 로그인 차단으로 구분한다. 서버의 로그인 차단은 06에서 만든다.
- Refresh Token 쿠키에 `Max-Age` 30분을 두었다. 브라우저를 다시 켜도 세션 만료 전이면 쿠키가 남는다.
- 서명용 비밀 키는 32자 이상이어야 서버가 시작된다.
- 401·429가 아닌 실패 응답과 서버에 닿지 못한 경우는 화면에서 "잠시 후 다시 시도"로 안내한다.

### 결정 (2026-10-15)

사용자가 위 "이 티켓에서 spec보다 먼저 정한 것" 중 네 가지를 모두 그대로 두기로 했다: 이메일 정규화, 화면의 로그인 차단(429) 구분, Refresh Token 쿠키 `Max-Age` 30분, 서명용 비밀 키 32자 이상.
