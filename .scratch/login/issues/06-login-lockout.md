# 06: 반복된 로그인 실패를 차단하기

**만들 것:** 같은 이메일로 로그인 실패가 반복되면 로그인 차단으로 추가 시도를 막고 사용자에게 이유를 안내한다. 정해진 시간이 지나면 다시 로그인할 수 있으며, 로그인에 성공하면 이전 실패 기록이 지워진다.

**Blocked by:** 01: 로그인하고 보호된 화면 보기.

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 14~18, 23 및 로그인 차단 규칙.

## 인수 조건

- [x] 이메일의 앞뒤 공백을 지우고 소문자로 바꾼 값을 사용자 조회와 로그인 실패 횟수 계산에 사용한다. 공백·대소문자만 다른 입력은 같은 이메일로 처리한다.
- [x] 실패 기록은 Redis에서 이메일별로 관리하고, 존재하지 않는 이메일도 같은 규칙으로 센다. 처음 4번의 실패는 HTTP 401과 "이메일 또는 비밀번호가 올바르지 않습니다"를 반환한다.
- [x] 마지막 실패로부터 15분이 지나면 실패 횟수가 사라진다. 그 전에 실패하면 횟수가 누적되고, 실패 기록의 만료 기준은 마지막 실패 시각으로 바뀐다.
- [x] 5번째 실패부터 HTTP 429와 로그인 차단 사실 및 "잠시 후 다시 시도" 안내를 반환한다. 차단 기간은 5번째 실패 시점부터 15분이다.
- [x] 로그인 차단 중에는 비밀번호를 대조하지 않고 HTTP 429를 반환한다. 올바른 비밀번호를 입력해도 동일하게 거절하며, 차단 기간이 끝나면 별도 조치 없이 다시 로그인할 수 있다.
- [x] 로그인에 성공하면 해당 이메일의 실패 기록을 지운다. 이후 로그인 실패는 이전에 누적된 횟수와 합쳐지지 않는다.
- [x] 화면 인증 모듈과 로그인 화면은 공통 실패(401), 로그인 차단(429), Redis 장애로 인한 일시 실패(503)를 구분해 안내한다. 없는 이메일과 틀린 비밀번호의 공통 메시지는 동일하게 유지한다.
- [x] 로그인 차단 기록을 다루는 중 Redis를 사용할 수 없으면 로그인은 HTTP 503과 "잠시 후 다시 시도"로 실패한다. 화면에서 비밀번호 오류나 로그인 차단으로 잘못 표시하지 않는다.
- [x] 서버 HTTP API 테스트에서 실제 PostgreSQL·Redis를 사용해 4번째와 5번째 실패의 응답 차이, 없는 이메일에 동일한 규칙 적용, 이메일 공백·대소문자 처리, 차단 중 올바른 비밀번호 거절을 확인한다.
- [x] 테스트용 시계로 15분 뒤 차단 해제, 마지막 실패 15분 뒤 횟수 만료, 만료 전 실패에 따른 기록 유지, 성공 후 실패 기록 초기화를 확인한다. Redis 내부 기록을 읽지 않고 이후 로그인 요청의 HTTP 결과로 검증한다.
- [x] 테스트용 Redis를 실제로 멈춰 로그인 차단 기록의 장애도 503으로 처리되는지 확인한다. 화면 인증 모듈 테스트로 세 가지 실패 종류를 구분해 전달하는지 확인한다.
- [x] E2E 시나리오 6인 "같은 이메일로 5번 실패 후 로그인 차단 안내, 이어서 올바른 비밀번호도 차단 안내"를 실제 브라우저와 실제 저장소로 통과시킨다. E2E에서 시간을 앞당기거나 차단 해제를 기다리지 않는다.
- [x] E2E 시나리오 1·5의 로그인 성공과 공통 실패 메시지도 유지한다. 테스트 이름·기댓값은 용어집과 spec을 따르고 실행 명령·결과 및 미검증 항목을 기록한다.

## 범위 경계

로그인 차단은 이메일을 기준으로 로그인 시도를 제한한다. 이미 발급된 Access Token이나 다른 기기의 세션을 폐기하는 기능은 추가하지 않는다. 토큰 교환이나 로그아웃을 사용하지 않아 02~05는 선행 조건이 아니다.

| 로그인 차단 테스트 반복 | `./gradlew test --tests '*LoginLockout*' --rerun-tasks` 3번 | 3번 모두 통과 (동시 요청 테스트가 우연히 통과하지 않는지 확인) |

| 화면 인증 모듈 테스트 | `cd web && npm test` | 26개 통과 (01부터 401·429·503을 구분해 알리는 테스트가 있어 화면 코드는 바꾸지 않음) |

서버 테스트로 확인한 것 (바꿔 끼운 시계 사용, HTTP 결과로만 판정):
- 4번째 실패까지 401 공통 메시지, 5번째 실패에 429와 "잠시 후 다시 시도" 안내
- 존재하지 않는 이메일도 같은 규칙, 앞뒤 공백·대소문자만 다른 이메일은 같은 이메일로 셈
- 로그인 차단 중에는 올바른 비밀번호도 429
- 5번째 실패 뒤 14분 59초에는 429, 15분에는 로그인 성공 (따로 할 일 없이 풀림)
- 4번 실패 뒤 15분이 지나면 다시 4번 실패해도 401 (횟수가 사라짐)
- 첫 실패, 10분 뒤 3번 더 실패, 다시 10분 뒤 실패하면 5번째로 429 (횟수가 이어지고 마지막 실패부터 15분을 셈)
- 로그인에 성공하면 이후 4번 실패해도 401 (이전 횟수와 합쳐지지 않음)
- 4번 실패한 뒤 올바른 비밀번호로 동시에 10번 시도하면 1번만 성공하고 나머지는 429
- Redis가 멈추면 틀린 비밀번호의 로그인도 503

**미검증**

- 로그인 차단 중에 비밀번호를 대조하지 않는 것: 코드(`AuthService.login`)로만 확인했다. HTTP 결과로는 대조했는지 알 수 없다.
- Redis 장애는 로그인 시도를 세는 첫 단계에서 503이 되는 것만 확인했다. 로그인 성공 뒤 실패 기록을 지우는 단계만 따로 장애를 일으키는 테스트는 없다.
- E2E에서 차단이 15분 뒤 풀리는 것은 확인하지 않았다 (티켓의 결정대로 시간을 앞당기거나 기다리지 않음). 서버 테스트로 확인했다.

**이 티켓에서 spec보다 먼저 정한 것**

- 로그인 차단 응답(429)의 안내 문장은 "로그인 시도가 너무 많습니다. 잠시 후 다시 시도해 주세요"로 한다. 화면의 기본 문장과 같다.
- 로그인 시도는 비밀번호를 대조하기 전에 한 번에 세고, 로그인에 성공하면 그 기록을 지운다. 그래서 4번 실패한 뒤 5번째 시도를 확인하는 동안 동시에 들어온 다른 시도는 올바른 비밀번호여도 429를 받는다. 동시 요청으로 5번 넘게 비밀번호를 찍어 보는 것을 막기 위해서다.
- 로그인 차단 중의 시도는 기록을 바꾸지 않는다. 그래서 차단 중에 계속 시도해도 차단 기간이 늘어나지 않는다.
- Redis에는 이메일을 그대로 쓰지 않고 해시로 바꿔 키로 쓴다.
- E2E는 로그인 차단 시나리오 전용 사용자(`e2e-lockout@example.com`)를 따로 두고, 시작할 때 E2E용 Redis(1번 데이터베이스)를 비운다. 다른 시나리오의 사용자가 차단되거나, 15분 안에 다시 돌린 E2E가 남은 차단 기록 때문에 실패하지 않게 하기 위해서다.
