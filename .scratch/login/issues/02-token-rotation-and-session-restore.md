# 02: 토큰 교환으로 새로고침 후 로그인 복원하기

**만들 것:** 사용자가 새로고침하거나 새 탭에서 앱을 열면 토큰 교환(Refresh Token을 내고 새 Access Token과 새 Refresh Token을 받는 일)으로 로그인을 복원한다. 세션 만료 이후에는 다시 로그인하도록 안내한다.

**Blocked by:** 01: 로그인하고 보호된 화면 보기.

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 5~6, 9~10, 21, 23 및 ADR-0001.

## 인수 조건

- [x] 현재 Refresh Token을 쿠키로 제출하면 HTTP 200과 새 Access Token을 받고, 새 Refresh Token 쿠키가 설정된다. 제출한 토큰은 직전 Refresh Token이 되어 더 이상 현재 Refresh Token으로 처리되지 않는다.
- [ ] 세션에는 사용자 식별자, 현재·직전 Refresh Token의 해시와 교환 시각, 지금까지 발급한 Refresh Token의 해시 목록이 연결된다. 04의 재사용 감지가 이전 토큰의 소속 세션을 판단할 수 있도록 세션이 유지되는 동안 기록을 보존한다.
- [x] 새 Access Token은 01과 같은 서명·내용·15분 유효 기간을 따른다. 새 Refresh Token은 무작위 문자열이며, 쿠키 속성과 경로 제한은 01의 규칙을 유지한다.
- [x] 로그인 또는 마지막 토큰 교환으로부터 30분이 지나면 세션 만료로 처리한다. 만료 전에 현재 Refresh Token으로 토큰 교환을 하면 그 시점부터 30분을 다시 센다. 토큰 교환을 계속하는 세션에는 최대 수명 상한을 두지 않는다.
- [x] Refresh Token이 없거나 알 수 없는 값이거나 세션 만료 이후이면 HTTP 401을 반환하고 Refresh Token 쿠키를 삭제한다.
- [x] Redis가 멈추면 토큰 교환은 HTTP 503과 "잠시 후 다시 시도" 안내로 실패한다.
- [ ] 앱이 시작될 때 토큰 교환을 한 번 시도한다. 새로고침과 새 탭 열기에서 성공하면 Access Token을 메모리에 두고 로그인 상태를 화면에 알린 뒤 보호된 화면을 사용할 수 있다. 화면은 저장소의 토큰을 직접 다루지 않고 화면 인증 모듈을 사용한다.
- [x] 로그인 복원에 실패하면 화면 인증 모듈은 Access Token을 보유한 상태로 남지 않고, 로그아웃 상태를 알려 로그인 화면으로 안내한다. Redis 장애 안내를 잘못된 비밀번호 안내로 바꾸지 않는다.
- [x] 서버 HTTP API 테스트는 실제 PostgreSQL·Redis와 바꿔 끼운 시계를 사용해 현재 토큰의 교환, 없는·알 수 없는 토큰 거절, 쿠키 설정·삭제를 확인한다. Redis 내부 값 대신 HTTP 결과로 검증한다.
- [x] 시간 테스트로 로그인 후 30분 만료, 마지막 교환 후 30분 만료, 교환에 따른 연장, 반복 교환 시 최대 수명 상한이 없음을 확인한다. 테스트용 Redis를 멈춰 토큰 교환 503도 확인한다.
- [x] 화면 인증 모듈 테스트로 앱 시작 시 한 번의 복원 시도, 성공 후 인증 요청과 상태 알림, 401·503 실패 처리를 확인한다.
- [x] E2E 시나리오 2인 "로그인 후 새로고침해도 같은 보호된 화면 사용"을 실제 브라우저와 실제 저장소로 통과시킨다. 시간은 앞당기지 않고 새로고침으로 토큰 교환을 일으킨다.
- [x] 테스트 이름과 기댓값은 용어집과 spec을 따른다. 실행 명령·결과를 기록하고 미검증 항목을 구분한다.

## 범위 경계

이 티켓의 화면 흐름은 앱 시작 시의 로그인 복원이다. 요청 도중 401에 대한 자동 복구는 03에서 추가한다. 직전·이전 Refresh Token의 유예 시간·재사용 감지와 동시 교환의 최종 규칙은 04에서 완성하며, 탭 간 교환 순서를 맞추는 기능은 추가하지 않는다.

## Comments

### 구현 기록 (2026-10-15)

**실행한 검증과 결과**

| 검증 | 명령 | 결과 |
|---|---|---|
| 서버 HTTP API 테스트 | `cd server && ./gradlew test` | 25개 통과. 이 티켓에서 더한 것: 토큰 교환 9개, Redis 장애 시 토큰 교환 503 1개, 여러 기기 세션의 토큰 교환 확인 |
| 화면 인증 모듈 테스트 | `cd web && npm test` | 12개 통과. 이 티켓에서 더한 것: 로그인 상태 복원 5개 |
| 화면 타입 검사·린트·빌드 | `npm run typecheck`, `npx oxlint`, `npm run build` | 오류 없음 |
| E2E 시나리오 1, 2, 5 | `cd e2e && npm test` (Chromium, Docker Compose의 PostgreSQL·Redis) | 3개 통과. 시나리오 2는 새로고침 뒤 같은 사용자 식별자가 보이고 Refresh Token 쿠키 값이 바뀐 것까지 확인 |

시간 테스트(바꿔 끼운 시계 사용)로 확인한 것:
- 로그인 후 29분 59초에는 토큰 교환 성공, 30분에는 세션 만료(401, 쿠키 삭제)
- 로그인 20분 뒤 토큰 교환하면 그때부터 30분을 다시 셈 (마지막 교환 후 29분 59초 성공, 30분 만료)
- 세션 만료 직전마다 토큰 교환을 200번(약 4일) 이어도 계속 성공 (최대 수명 상한 없음)
- 토큰 교환으로 받은 Access Token도 15분 뒤부터 거절

**미검증**

- 세션에 연결된 직전 Refresh Token의 해시·교환 시각, 지금까지 발급한 Refresh Token의 해시 목록: 코드(`server/src/main/resources/auth/rotate-refresh-token.lua`)로만 확인했다. HTTP로 보이는 쓰임은 04의 유예 시간·재사용 감지에서 검증한다.
- 새 탭 열기에서의 로그인 상태 복원: 새로고침과 같은 코드 경로지만 E2E로는 새로고침만 확인했다. 새 탭은 04의 E2E 시나리오 3에서 검증한다.

**04 전까지의 알려진 위험**

- 유예 시간이 아직 없어서, 직전 Refresh Token을 내면 10초 안이어도 401을 받고 Refresh Token 쿠키가 지워진다. 그래서 탭 두 개가 거의 동시에 로그인 상태를 복원하면 한쪽 때문에 로그아웃될 수 있다. 04에서 유예 시간으로 해결한다.

**이 티켓에서 spec보다 먼저 정한 것**

- 화면 인증 모듈의 로그인 상태에 "복원 중" 상태를 더했다. 앱이 시작될 때 잠깐 로그인 화면이 보였다가 사라지지 않도록, 복원하는 동안 "로그인 상태를 확인하는 중입니다"를 보여 준다.
- 로그아웃 상태에 안내 문구를 함께 실을 수 있게 했다. 복원이 503이나 연결 실패로 끝나면 로그인 화면에 "잠시 후 다시 시도해 주세요"를 보여 준다. 비밀번호 오류 안내로 바꾸지 않기 위해서다.
- 복원 중 401·503이 아닌 실패 응답과 서버에 닿지 못한 경우도 "잠시 후 다시 시도해 주세요"로 안내한다. 01의 로그인 실패 처리와 같은 규칙이다.
