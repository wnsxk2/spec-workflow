# 03: Access Token이 만료되어도 작업 이어가기

**만들 것:** 사용자가 보호된 기능을 사용하다 Access Token이 만료되어도 화면 인증 모듈이 토큰 교환 후 요청을 다시 보내 작업을 이어 간다. 토큰 교환에 실패하면 다시 로그인하도록 안내한다.

**Blocked by:** 02: 토큰 교환으로 새로고침 후 로그인 복원하기.

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 2, 4, 10, 20 및 화면 인증 모듈의 인증 요청 보내기 계약.

## 인수 조건

- [ ] 화면의 보호된 요청은 화면 인증 모듈을 통해 보내며 메모리의 Access Token을 붙인다. 정상 응답에는 불필요한 토큰 교환을 하지 않는다.
- [ ] 보호된 요청에서 HTTP 401을 받으면 토큰 교환을 한 번 수행한다. 성공하면 메모리의 Access Token을 새 값으로 바꾸고, 원래 요청의 메서드·본문 등 의미를 보존해 같은 요청을 한 번 다시 보낸다.
- [ ] 다시 보낸 요청도 HTTP 401이면 토큰 교환·재요청을 반복하지 않는다. 토큰 교환 요청 자체를 보호된 요청의 401 복구 처리에 넣어 반복 호출하지 않는다.
- [ ] 한 탭 안에서 여러 보호된 요청이 동시에 HTTP 401을 받으면 진행 중인 토큰 교환 하나를 함께 기다린다. 성공하면 각 원래 요청을 새 Access Token으로 한 번씩 다시 보내고, 실패하면 어느 요청도 이전 Access Token으로 재요청하지 않는다.
- [ ] 토큰 교환이 HTTP 401·503 또는 네트워크 오류로 실패하면 메모리의 Access Token을 지우고 로그아웃 상태를 화면에 알려 로그인 화면으로 안내한다. 503의 "잠시 후 다시 시도" 안내를 로그인 정보 오류로 바꾸지 않는다.
- [ ] 탭과 탭 사이에서 토큰 교환 순서를 맞추는 기능은 도입하지 않는다. 여러 탭의 동시 교환은 04의 유예 시간 규칙으로 처리한다.
- [ ] 화면 인증 모듈 테스트로 정상 요청, 401 후 교환 성공·원래 요청 재전송, 두 번째 401에서 반복 중단, 교환 실패 후 상태 변경을 확인한다. 모듈 내부 변수 대신 요청 결과·서버로 보낸 요청·공개된 상태 알림을 검증한다.
- [ ] 화면 인증 모듈 테스트에서 여러 동시 401에 대해 토큰 교환이 한 번만 호출되고 각 원래 요청이 한 번만 재전송되는지 확인한다. 공통 교환 실패 시 모든 대기 요청이 실패 처리되는지도 확인한다.
- [ ] Access Token의 실제 15분 만료와 토큰 교환 HTTP 계약은 01·02의 서버 테스트로, 화면의 자동 복구는 가짜 서버 응답을 사용하는 화면 인증 모듈 테스트로 검증한다. E2E에서 시간을 앞당기거나 15분을 기다리는 시나리오는 추가하지 않는다.
- [ ] 기존 로그인·새로고침 E2E가 계속 통과한다. 테스트 이름·기댓값은 용어집과 spec을 따르고 실행 명령·결과 및 미검증 항목을 기록한다.
