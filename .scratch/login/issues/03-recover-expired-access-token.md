# 03: Access Token이 만료되어도 작업 이어가기

**만들 것:** 사용자가 보호된 기능을 사용하다 Access Token이 만료되어도 화면 인증 모듈이 토큰 교환 후 요청을 다시 보내 작업을 이어 간다. 토큰 교환에 실패하면 다시 로그인하도록 안내한다.

**Blocked by:** 02: 토큰 교환으로 새로고침 후 로그인 복원하기.

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 2, 4, 10, 20 및 화면 인증 모듈의 인증 요청 보내기 계약.

## 인수 조건

- [x] 화면의 보호된 요청은 화면 인증 모듈을 통해 보내며 메모리의 Access Token을 붙인다. 정상 응답에는 불필요한 토큰 교환을 하지 않는다.
- [x] 보호된 요청에서 HTTP 401을 받으면 토큰 교환을 한 번 수행한다. 성공하면 메모리의 Access Token을 새 값으로 바꾸고, 원래 요청의 메서드·본문 등 의미를 보존해 같은 요청을 한 번 다시 보낸다.
- [x] 다시 보낸 요청도 HTTP 401이면 토큰 교환·재요청을 반복하지 않는다. 토큰 교환 요청 자체를 보호된 요청의 401 복구 처리에 넣어 반복 호출하지 않는다.
- [x] 한 탭 안에서 여러 보호된 요청이 동시에 HTTP 401을 받으면 진행 중인 토큰 교환 하나를 함께 기다린다. 성공하면 각 원래 요청을 새 Access Token으로 한 번씩 다시 보내고, 실패하면 어느 요청도 이전 Access Token으로 재요청하지 않는다.
- [x] 토큰 교환이 HTTP 401·503 또는 네트워크 오류로 실패하면 메모리의 Access Token을 지우고 로그아웃 상태를 화면에 알려 로그인 화면으로 안내한다. 503의 "잠시 후 다시 시도" 안내를 로그인 정보 오류로 바꾸지 않는다.
- [x] 탭과 탭 사이에서 토큰 교환 순서를 맞추는 기능은 도입하지 않는다. 여러 탭의 동시 교환은 04의 유예 시간 규칙으로 처리한다.
- [x] 화면 인증 모듈 테스트로 정상 요청, 401 후 교환 성공·원래 요청 재전송, 두 번째 401에서 반복 중단, 교환 실패 후 상태 변경을 확인한다. 모듈 내부 변수 대신 요청 결과·서버로 보낸 요청·공개된 상태 알림을 검증한다.
- [x] 화면 인증 모듈 테스트에서 여러 동시 401에 대해 토큰 교환이 한 번만 호출되고 각 원래 요청이 한 번만 재전송되는지 확인한다. 공통 교환 실패 시 모든 대기 요청이 실패 처리되는지도 확인한다.
- [x] Access Token의 실제 15분 만료와 토큰 교환 HTTP 계약은 01·02의 서버 테스트로, 화면의 자동 복구는 가짜 서버 응답을 사용하는 화면 인증 모듈 테스트로 검증한다. E2E에서 시간을 앞당기거나 15분을 기다리는 시나리오는 추가하지 않는다.
- [x] 기존 로그인·새로고침 E2E가 계속 통과한다. 테스트 이름·기댓값은 용어집과 spec을 따르고 실행 명령·결과 및 미검증 항목을 기록한다.

## Comments

### 구현 기록 (2026-10-15)

**실행한 검증과 결과**

| 검증 | 명령 | 결과 |
|---|---|---|
| 화면 인증 모듈 테스트 | `cd web && npm test` | 22개 통과. 이 티켓에서 더한 것: "Access Token 만료 뒤 자동 복구" 9개 |
| 화면 타입 검사·린트·빌드 | `npm run typecheck`, `npx oxlint`, `npm run build` | 오류 없음 |
| 서버 HTTP API 테스트 | `cd server && ./gradlew test` | 33개 통과 (서버 코드는 바뀌지 않음. Access Token 15분 만료와 토큰 교환 계약은 01·02의 테스트가 확인) |
| E2E 시나리오 1, 2, 3, 5 | `cd e2e && npm test` | 4개 통과 (이 티켓에서 더한 시나리오 없음, 시간을 앞당기지 않음) |

화면 인증 모듈 테스트로 확인한 것 (가짜 서버 응답 사용):
- 정상 응답에는 토큰 교환을 하지 않는다
- 401을 받으면 토큰 교환을 한 번 하고, 원래 요청을 메서드·본문·헤더 그대로 새 Access Token으로 한 번 다시 보낸다
- 다시 보낸 요청도 401이면 토큰 교환과 재요청을 반복하지 않는다
- 한 탭에서 세 요청이 동시에 401을 받으면 토큰 교환은 한 번, 각 요청은 한 번씩 다시 보낸다
- 토큰 교환이 401이면 Access Token을 지우고 로그아웃 상태를 알리며, 기다리던 요청은 다시 보내지 않는다
- 토큰 교환이 503이거나 서버에 닿지 못하면 로그아웃 상태와 함께 "잠시 후 다시 시도해 주세요" 안내를 알린다
- 아래 "spec보다 먼저 정한 것" 세 가지

**미검증**

- 화면에서 15분이 지나 실제로 401을 받고 자동 복구되는 흐름 전체: 티켓의 결정대로 E2E로 시간을 앞당기거나 기다리지 않았다. 서버 쪽 만료(01·02 서버 테스트)와 화면 쪽 복구(이 티켓의 화면 인증 모듈 테스트)를 따로 확인했다.
- 다시 보낼 수 없는 본문: 원래 요청을 다시 보낼 때 같은 요청 내용(init)을 그대로 쓴다. 본문이 문자열·FormData·Blob이면 문제없지만, 한 번 읽으면 사라지는 스트림(ReadableStream)이면 다시 보낼 수 없다. 지금 화면의 보호된 요청은 `GET /api/me`뿐이라 영향은 없다.

**이 티켓에서 spec보다 먼저 정한 것**

- Access Token 없이 보낸 요청의 401에는 토큰 교환을 하지 않는다. 만료된 Access Token이 아니라 애초에 로그인하지 않은 경우이기 때문이다.
- 토큰 교환이 이미 끝난 뒤에 도착한, 이전 Access Token으로 보낸 요청의 401은 새로 교환하지 않고 이미 받은 새 Access Token으로 바로 다시 보낸다. 쓸데없는 토큰 교환을 줄이기 위해서다.
- 토큰 교환 실패로 로그아웃된 뒤에 도착한 401에는 다시 토큰 교환을 하지 않는다. 이미 로그인 화면으로 안내했기 때문이다.
