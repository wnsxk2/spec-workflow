# 04: 여러 탭의 토큰 교환을 허용하고 재사용 감지하기

**만들 것:** 사용자가 여러 탭을 동시에 열거나 토큰 교환 요청을 짧은 시간 안에 다시 보내도 로그인을 이어 간다. 유예 시간(직전 Refresh Token의 재제출을 허용하는 10초)을 벗어나거나 더 오래된 토큰이 제출되면 재사용 감지로 해당 세션만 폐기한다.

**Blocked by:** 02: 토큰 교환으로 새로고침 후 로그인 복원하기.

**Status:** ready-for-agent

**근거:** 로그인 spec의 사용자 스토리 6~8, 19~20, 24 및 ADR-0001.

## 인수 조건

- [ ] 현재 Refresh Token으로 토큰 교환하면 제출된 토큰을 직전 Refresh Token으로 기록한다. 직전 Refresh Token이 교환 후 10초 이내에 다시 제출되면 재사용 감지로 보지 않고 방금 발급한 것과 같은 Refresh Token을 반환하며, Access Token은 새로 발급한다.
- [ ] 직전 Refresh Token의 반복 제출로 새 Refresh Token을 계속 만들거나 최초 교환 시각을 다시 시작하지 않는다. 네트워크 문제로 첫 응답을 받지 못한 요청도 10초 이내 재시도로 같은 Refresh Token을 받을 수 있다.
- [ ] 같은 Refresh Token을 낸 요청이 동시에 들어와도 현재 토큰을 새 토큰으로 바꾸는 처리는 정확히 한 번만 일어난다. 토큰 교환을 원자적으로 처리해 중간 상태에 다른 요청이 끼어들지 않으며, 나머지 요청은 유예 시간 규칙으로 같은 새 Refresh Token을 받는다.
- [ ] 유예 시간에 같은 값을 돌려주기 위해 새 Refresh Token의 원래 값을 10초 동안만 보관한다. 그 밖의 세션 기록은 해시로 보관하고, 유예 시간용 원래 값이 이후에도 남지 않도록 한다.
- [ ] 직전 Refresh Token이 교환 후 10초를 지나 제출되면 재사용 감지로 해당 세션을 폐기하고 HTTP 401과 Refresh Token 쿠키 삭제를 반환한다.
- [ ] 두 단계 이전 이상의 Refresh Token은 직전 교환으로부터 10초 이내라도 재사용 감지로 해당 세션을 폐기하고 HTTP 401과 쿠키 삭제를 반환한다.
- [ ] 재사용 감지로 세션 폐기된 이후에는 그 세션의 최신 Refresh Token도 사용할 수 없다. 같은 사용자의 다른 세션은 유지되어 토큰 교환과 보호된 요청을 계속할 수 있다.
- [ ] 세션 폐기 이후 새로고침 등으로 로그인 복원을 시도하면 02의 실패 처리를 통해 로그인 화면으로 안내된다. 이미 발급된 Access Token은 ADR-0001에 따라 자신의 만료 시각까지 유효하다.
- [ ] 여러 탭의 요청을 화면에서 순서대로 묶는 기능이나 Web Locks(탭끼리 실행 순서를 맞추는 브라우저 기능)를 도입하지 않는다.
- [ ] 서버 HTTP API 테스트에서 실제 PostgreSQL·Redis와 바꿔 끼운 시계로 10초 이내의 동일 토큰 반환, 10초가 지난 직전 토큰 거절, 두 단계 이전 토큰 거절을 확인한다. 유예 시간의 경계 전후와 반복 제출을 검증한다.
- [ ] 동시 HTTP 요청 테스트에서 반환된 Refresh Token이 하나로 일치하고 그 토큰으로 다음 교환이 성공하는지 확인한다. 재사용 감지 후 최신 토큰 거절과 다른 세션의 교환 성공도 확인하며, Redis 내부 값을 직접 읽어 판정하지 않는다.
- [ ] E2E 시나리오 3인 "로그인 후 같은 화면을 탭 5개로 동시에 열기"를 통과시킨다. 모든 탭이 로그인 상태이며 이후 아무 탭이나 새로고침해도 유지된다. 실제 브라우저와 실제 저장소를 사용하고 시간을 앞당기지 않는다.
- [ ] 실행 명령·결과와 미검증 항목을 기록한다. 테스트 이름과 기댓값은 용어집 및 spec을 따르며 기존 로그인·복원 검증도 유지한다.

## 범위 경계

03의 한 탭 안 동시 401 처리와 별개로, 이 티켓은 서버의 토큰 교환 규칙과 앱 시작 시 여러 탭의 복원을 완성한다. 로그인 화면 안내는 02의 복원 실패 경로로 검증하므로 03은 선행 조건이 아니다.
