이 스킬은 현재 대화 컨텍스트와 코드베이스에 대한 이해를 바탕으로 스펙을 만든다. 사용자를 인터뷰하지 않는다. 이미 아는 것을 종합하기만 한다.

이슈 트래커와 트리아지 라벨 용어는 미리 제공되었어야 한다. 그렇지 않다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내한다.

## 절차

1. 아직 하지 않았다면 저장소를 탐색해 코드베이스의 현재 상태를 파악한다. 스펙 전체에서 프로젝트 도메인 용어집의 어휘를 사용하고, 손대는 영역의 ADR을 존중한다.

2. 기능을 테스트할 시임(seam)을 스케치한다. 새 시임보다 기존 시임을 우선한다. 가능한 한 가장 높은 시임을 쓴다. 새 시임이 필요하다면 가능한 한 높은 지점에 제안한다. 코드베이스 전체에서 시임은 적을수록 좋으며, 이상적인 개수는 하나다.

   이 시임들이 사용자의 기대와 맞는지 사용자에게 확인받는다.

3. 아래 템플릿으로 스펙을 작성한 뒤 프로젝트 이슈 트래커에 게시한다. `ready-for-agent` 트리아지 라벨을 적용한다. 추가 트리아지는 필요 없다.

## 구현 결정

내려진 구현 결정의 목록. 다음을 포함할 수 있다:

- 새로 만들거나 수정할 모듈
- 수정될 그 모듈들의 인터페이스
- 개발자가 내린 기술적 설명
- 아키텍처 결정
- 스키마 변경
- API 계약
- 구체적인 상호작용

구체적인 파일 경로나 코드 스니펫은 넣지 **않는다**. 금방 낡을 수 있기 때문이다.

예외: 프로토타입이 산문보다 결정을 더 정확하게 담아내는 스니펫(상태 머신, 리듀서, 스키마, 타입 형태)을 만들어 냈다면, 해당 결정 안에 인라인으로 넣고 프로토타입에서 나온 것임을 짧게 적는다. 동작하는 데모가 아니라 결정이 풍부한 부분, 즉 중요한 부분만 남기도록 다듬는다.

## 테스트 결정

내려진 테스트 결정의 목록. 다음을 포함한다:

- 좋은 테스트란 무엇인지에 대한 설명 (구현 세부사항이 아니라 외부 동작만 테스트한다)
- 어떤 모듈을 테스트할 것인지
- 테스트의 선례 (즉, 코드베이스에 있는 비슷한 유형의 테스트)
