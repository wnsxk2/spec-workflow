# 깊게 만들기(Deepening)

얕은 모듈 묶음을 그 의존성을 고려해 안전하게 깊게 만드는 방법. [SKILL.md](SKILL.md)의 용어 **모듈**, **인터페이스**, **시임**, **어댑터**를 전제로 한다.

## 의존성 분류

깊게 만들 후보를 평가할 때 그 의존성을 분류한다. 분류에 따라 깊어진 모듈을 시임 너머로 어떻게 테스트할지가 정해진다.

### 1. 프로세스 내부 (In-process)

순수 계산, 메모리 내 상태, I/O 없음. 언제나 깊게 만들 수 있다: 모듈들을 합치고 새 인터페이스를 통해 직접 테스트한다. 어댑터가 필요 없다.

### 2. 로컬 대체 가능 (Local-substitutable)

로컬 테스트 대역이 있는 의존성(Postgres 대신 PGLite, 인메모리 파일 시스템 등). 대역이 존재하면 깊게 만들 수 있다. 깊어진 모듈은 테스트 스위트에서 대역을 실행한 채로 테스트한다. 시임은 내부에 있으며, 모듈의 외부 인터페이스에 포트를 두지 않는다.

### 3. 원격이지만 소유함 (포트와 어댑터)

네트워크 경계 너머에 있는 직접 소유한 서비스(마이크로서비스, 내부 API). 시임에 **포트**(인터페이스)를 정의한다. 깊은 모듈이 로직을 소유하고, 전송 계층은 **어댑터**로 주입한다. 테스트는 인메모리 어댑터를 쓰고, 프로덕션은 HTTP/gRPC/큐 어댑터를 쓴다.

권고 형태: *"시임에 포트를 정의하고, 프로덕션용 HTTP 어댑터와 테스트용 인메모리 어댑터를 구현해서, 네트워크를 가로질러 배포되더라도 로직이 하나의 깊은 모듈 안에 있도록 하라."*

### 4. 진짜 외부 (Mock)

직접 통제하지 않는 서드파티 서비스(Stripe, Twilio 등). 깊어진 모듈은 외부 의존성을 주입된 포트로 받고, 테스트는 목 어댑터를 제공한다.

## 시임 규율

- **어댑터가 하나면 가설상의 시임이다. 둘이면 진짜 시임이다.** 최소 두 개의 어댑터(보통 프로덕션 + 테스트)가 정당화되지 않는 한 포트를 도입하지 않는다. 어댑터가 하나뿐인 시임은 그저 간접 계층일 뿐이다.
- **내부 시임 vs 외부 시임.** 깊은 모듈은 인터페이스의 외부 시임뿐 아니라 내부 시임(구현에 비공개이며 자체 테스트가 사용하는)도 가질 수 있다. 테스트가 쓴다는 이유만으로 내부 시임을 인터페이스를 통해 노출하지 않는다.

## 테스트 전략: 겹쳐 쌓지 말고 대체하라

- 깊어진 모듈의 인터페이스에 테스트가 생기면, 얕은 모듈에 대한 기존 단위 테스트는 낭비가 된다. 삭제한다.
- 깊어진 모듈의 인터페이스에 새 테스트를 작성한다. **인터페이스가 곧 테스트 표면이다.**
- 테스트는 내부 상태가 아니라 인터페이스를 통해 관찰 가능한 결과를 단언한다.
- 테스트는 구현이 아니라 동작을 서술하므로 내부 리팩터링에도 살아남아야 한다. 구현이 바뀔 때 테스트도 바뀌어야 한다면, 그 테스트는 인터페이스 너머를 테스트하고 있는 것이다.
