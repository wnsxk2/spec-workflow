# 테스트 주도 개발

TDD는 red → green 루프다. 이 스킬은 그 루프가 남겨 둘 가치가 있는 테스트를 만들어 내도록 하는 참고 자료다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴, 그리고 루프의 규칙을 다룬다. 모든 절은 매 사이클마다 적용된다. 루프가 끝난 뒤가 아니라 루프 전과 도중에 참고한다.

코드베이스를 탐색할 때 `GLOSSARY.md`가 있으면 읽어서 테스트 이름과 인터페이스 용어가 프로젝트의 도메인 언어와 맞도록 하고, 손대는 영역의 ADR을 존중한다.

## 좋은 테스트란

테스트는 구현 세부사항이 아니라 공개 인터페이스를 통해 동작을 검증한다. 코드는 통째로 바뀔 수 있어도 테스트는 바뀌지 않아야 한다. 좋은 테스트는 명세처럼 읽힌다. "사용자는 유효한 장바구니로 결제할 수 있다"는 어떤 기능이 존재하는지 정확히 알려 주며, 내부 구조에 관심이 없으므로 리팩터링에도 살아남는다.

예시는 [tests.md](tests.md)를, 모킹 지침은 [mocking.md](mocking.md)를 참고한다.

## 시임(seam): 테스트를 두는 곳

**시임**은 테스트하는 공개 경계로, 내부로 손을 뻗지 않고 동작을 관찰할 수 있는 인터페이스다. 테스트는 언제나 시임에 두며, 내부 구현을 대상으로 하지 않는다.

**미리 합의한 시임에서만 테스트한다.** 어떤 테스트든 작성하기 전에 테스트할 시임을 적어 두고 사용자에게 확인받는다. 확인받지 않은 시임에는 테스트를 작성하지 않는다. 모든 것을 테스트할 수는 없으므로, 시임을 미리 합의하는 것이 테스트 노력을 모든 엣지 케이스가 아닌 핵심 경로와 복잡한 로직에 집중시키는 방법이다.

다음과 같이 묻는다: "공개 인터페이스는 무엇이고, 어떤 시임을 테스트해야 할까요?" 제안하는 각 시임에는 그것이 잡아내는 것과 놓치는 것을 한 줄로 덧붙인다.

인터페이스의 형태 자체가 문제일 때(모듈이 얼마나 깊은지, 시임이 어디에 있어야 하는지, 인터페이스가 무엇을 노출해야 하는지) Skill 도구로 "codebase-design"을 호출해 용어를 확인한다. 그 스킬은 모듈, 인터페이스, 깊이, 시임, 어댑터, 레버리지, 지역성 용어의 공통 출처이며, 세션으로 진행하는 것이 아니라 참고 자료로 활용한다.

## 안티패턴

- **구현에 결합됨**: 내부 협력 객체를 모킹하거나, private 메서드를 테스트하거나, 우회 경로로 검증한다(인터페이스를 쓰는 대신 데이터베이스를 직접 조회하는 식). 징후: 동작은 그대로인데 리팩터링하면 테스트가 깨진다.
- **동어반복적**: 단언문이 코드와 같은 방식으로 기댓값을 다시 계산한다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 손으로 도출한 스냅샷, 자기 자신과 같다고 단언하는 상수). 그래서 구조상 항상 통과하며 코드와 어긋날 수가 없다. 기댓값은 독립적인 진실의 출처에서 와야 한다: 이미 검증된 리터럴, 직접 풀어 본 예제, 스펙.
- **수평 슬라이싱**: 테스트를 전부 먼저 쓰고 구현을 전부 나중에 한다. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증한다. 사용자에게 보이는 동작이 아니라 _모양_을 테스트하게 되고, 테스트가 실제 변경에 둔감해지며, 구현을 이해하기도 전에 테스트 구조에 묶인다. 대신 **수직 슬라이스**로 작업한다: 테스트 하나 → 구현 하나 → 반복. 각 테스트는 직전 사이클에서 배운 것에 반응하는 **예광탄(tracer bullet)**이다.

## 루프의 규칙

- **green 전에 red.** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼만 코드를 작성한다. 앞으로의 테스트를 예상하거나 추측성 기능을 더하지 않는다.
- **한 번에 한 슬라이스.** 사이클마다 시임 하나, 테스트 하나, 최소한의 구현 하나.
- **리팩터링은 루프의 일부가 아니다.** 리팩터링은 red → green 구현 사이클이 아니라 리뷰 단계(`code-review` 스킬 참고)에 속한다.
