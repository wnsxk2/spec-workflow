# GLOSSARY.md 형식

## 구조

```md
# {컨텍스트 이름}

{이 컨텍스트가 무엇이고 왜 존재하는지에 대한 한두 문장 설명.}

## 용어

**주문(Order)**:
{용어에 대한 한두 문장 설명}
_피할 말_: 구매, 거래

**청구서(Invoice)**:
배송 후 고객에게 보내는 결제 요청.
_피할 말_: 계산서, 결제 요청

**고객(Customer)**:
주문을 하는 개인 또는 조직.
_피할 말_: 클라이언트, 구매자, 계정
```

## 규칙

- **주관을 가진다.** 같은 개념에 여러 단어가 있으면 가장 좋은 하나를 고르고 나머지는 `_피할 말_` 아래에 나열한다.
- **정의는 짧게 유지한다.** 최대 한두 문장. 무엇을 *하는지*가 아니라 무엇*인지*를 정의한다.
- **이 프로젝트의 컨텍스트에 고유한 용어만 넣는다.** 일반적인 프로그래밍 개념(타임아웃, 오류 타입, 유틸리티 패턴)은 프로젝트가 아무리 많이 쓰더라도 넣지 않는다. 용어를 추가하기 전에 묻는다: 이것은 이 컨텍스트에 고유한 개념인가, 일반적인 프로그래밍 개념인가? 전자만 들어간다.
- **자연스러운 묶음이 생기면 용어를 소제목 아래로 묶는다.** 모든 용어가 하나의 응집된 영역에 속한다면 평평한 목록도 괜찮다.

## 단일 컨텍스트 vs 다중 컨텍스트 저장소

**단일 컨텍스트 (대부분의 저장소):** 저장소 루트에 `GLOSSARY.md` 하나.

**다중 컨텍스트:** 저장소 루트의 `GLOSSARY-MAP.md`가 컨텍스트 목록, 각 컨텍스트의 위치, 그리고 서로의 관계를 나열한다:

```md
# 용어집 맵

## 컨텍스트

- [주문(Ordering)](./src/ordering/GLOSSARY.md): 고객 주문을 접수하고 추적한다
- [청구(Billing)](./src/billing/GLOSSARY.md): 청구서를 발행하고 결제를 처리한다
- [출고(Fulfillment)](./src/fulfillment/GLOSSARY.md): 창고 피킹과 배송을 관리한다

## 관계

- **주문 → 출고**: 주문은 `OrderPlaced` 이벤트를 발행하고, 출고는 이를 소비해 피킹을 시작한다
- **출고 → 청구**: 출고는 `ShipmentDispatched` 이벤트를 발행하고, 청구는 이를 소비해 청구서를 발행한다
- **주문 ↔ 청구**: `CustomerId`와 `Money` 타입을 공유한다
```

스킬은 어떤 구조가 적용되는지 추론한다:

- `GLOSSARY-MAP.md`가 있으면 그것을 읽어 컨텍스트를 찾는다
- 루트 `GLOSSARY.md`만 있으면 단일 컨텍스트다
- 둘 다 없으면 첫 용어가 확정될 때 루트 `GLOSSARY.md`를 만든다

여러 컨텍스트가 있으면 현재 주제가 어느 컨텍스트와 관련되는지 추론한다. 불분명하면 묻는다.
