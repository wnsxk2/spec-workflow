# 도메인 모델링

설계하는 동안 프로젝트의 도메인 모델을 능동적으로 구축하고 다듬는다. 이것은 *능동적인* 규율이다: 용어에 이의를 제기하고, 엣지 케이스 시나리오를 만들어 내고, 용어집과 결정이 굳어지는 바로 그 순간 기록한다. (어휘를 위해 `GLOSSARY.md`를 *읽기만* 하는 것은 이 스킬이 아니다. 그것은 어떤 스킬이든 할 수 있는 한 줄짜리 습관이다. 이 스킬은 모델을 소비할 때가 아니라 바꿀 때 쓴다.)

## 파일 구조

대부분의 저장소는 단일 컨텍스트다:

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `GLOSSARY-MAP.md`가 있으면 저장소에 여러 컨텍스트가 있는 것이다. 맵은 각 컨텍스트가 어디에 있는지 가리킨다:

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전반의 결정
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 컨텍스트별 결정
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

파일은 필요할 때 만든다: 쓸 내용이 생겼을 때만. `GLOSSARY.md`가 없으면 첫 용어가 확정될 때 만든다. `docs/adr/`가 없으면 첫 ADR이 필요할 때 만든다.

## 세션 중에

### 용어집과 대조해 이의를 제기한다

사용자가 `GLOSSARY.md`의 기존 언어와 충돌하는 용어를 쓰면 즉시 지적한다. "용어집은 '취소'를 X로 정의하는데, 지금은 Y를 뜻하시는 것 같습니다. 어느 쪽인가요?"

### 흐릿한 언어를 날카롭게 한다

사용자가 모호하거나 여러 뜻으로 쓰이는 용어를 쓰면 정확한 표준 용어를 제안한다. "'계정'이라고 하셨는데, 고객(Customer)인가요 사용자(User)인가요? 둘은 다른 것입니다."

### 구체적인 시나리오로 논의한다

도메인 관계를 논의할 때는 구체적인 시나리오로 스트레스 테스트한다. 엣지 케이스를 찌르는 시나리오를 만들어 내서, 사용자가 개념 사이의 경계를 정확히 말하도록 만든다.

### 코드와 교차 확인한다

사용자가 무언가가 어떻게 동작하는지 말하면, 코드도 그렇게 되어 있는지 확인한다. 모순을 발견하면 드러낸다: "코드는 주문 전체를 취소하는데, 방금 부분 취소가 가능하다고 하셨습니다. 어느 쪽이 맞나요?"

### GLOSSARY.md를 그 자리에서 갱신한다

용어가 확정되면 바로 그 자리에서 `GLOSSARY.md`를 갱신한다. 모아 두었다가 한꺼번에 하지 않는다: 생기는 즉시 기록한다. 형식은 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)를 따른다.

`GLOSSARY.md`에는 구현 세부사항이 전혀 없어야 한다. `GLOSSARY.md`를 스펙, 메모장, 구현 결정 보관소로 취급하지 않는다. 용어집이며 그 외에는 아무것도 아니다.

### ADR은 아껴서 제안한다

다음 세 가지가 모두 참일 때만 ADR 작성을 제안한다:

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 의미 있다
2. **맥락 없이는 의외다**: 미래의 독자가 "왜 이렇게 했지?"라고 궁금해할 것이다
3. **실제 트레이드오프의 결과다**: 진짜 대안들이 있었고, 구체적인 이유로 그중 하나를 골랐다

셋 중 하나라도 빠지면 ADR을 건너뛴다. 형식은 [ADR-FORMAT.md](./ADR-FORMAT.md)를 따른다.
