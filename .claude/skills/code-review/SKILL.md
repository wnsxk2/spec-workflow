---

`HEAD`와 사용자가 지정한 고정 기준점 사이의 diff를 두 축으로 리뷰한다:

- **표준(Standards)**: 코드가 이 저장소에 문서화된 코딩 표준을 따르는가?
- **스펙(Spec)**: 코드가 원래의 이슈 / 스펙을 충실히 구현하는가?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브 에이전트**로 실행하고, 이 스킬이 그 결과를 취합한다.

이슈 트래커 정보는 미리 제공되었어야 한다. 그렇지 않다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내한다.

## 절차

### 1. 고정 기준점 확정

사용자가 말한 것이 고정 기준점이다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 물어본다.

diff 명령을 한 번 정해 둔다: `git diff <fixed-point>...HEAD` (점 세 개 — merge-base를 기준으로 비교한다). 커밋 목록도 `git log <fixed-point>..HEAD --oneline`으로 기록해 둔다.

더 진행하기 전에 기준점이 실제로 해석되는지(`git rev-parse <fixed-point>`), diff가 비어 있지 않은지 확인한다. 잘못된 ref나 빈 diff는 두 병렬 서브 에이전트 안이 아니라 여기서 실패해야 한다.

### 2. 스펙 출처 찾기

원래의 스펙을 다음 순서로 찾는다:

1. 커밋 메시지 안의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). 트래커 문서의 워크플로에 따라 가져온다.
2. 사용자가 인자로 넘긴 경로.
3. `docs/`, `specs/`, `.scratch/` 아래에서 브랜치 이름이나 기능과 일치하는 스펙 파일.
4. 아무것도 찾지 못하면 사용자에게 스펙이 어디 있는지 묻는다. 스펙이 없다고 하면 **스펙** 서브 에이전트는 건너뛰고 "사용 가능한 스펙 없음"으로 보고한다.

### 3. 표준 출처 찾기

저장소에서 코드 작성 방식을 문서화한 파일을 모두 찾는다. `CODING_STANDARDS.md`나 `CONTRIBUTING.md`가 존재하면 반드시 목록에 포함한다.

저장소가 무엇을 문서화했든 그와 별개로, 표준 축은 항상 아래의 **스멜 기준선(smell baseline)**을 함께 적용한다. 이는 Fowler의 코드 스멜(_Refactoring_, 3장) 중 고정된 일부로, 저장소에 아무 문서가 없어도 적용된다. 두 가지 규칙이 이를 구속한다:

- **저장소가 우선한다.** 문서화된 저장소 표준이 언제나 이긴다. 기준선이 지적할 만한 것을 저장소 표준이 승인한다면 그 스멜은 지적하지 않는다.
- **언제나 판단의 문제다.** 각 스멜은 딱 잘라 말하는 위반이 아니라 이름 붙은 휴리스틱("Feature Envy 가능성")이다. 여기의 다른 표준과 마찬가지로, 도구가 이미 강제하는 것은 건너뛴다.

각 스멜은 *무엇인가* → *어떻게 고치는가* 형식으로 읽고, diff와 대조한다:

- **Mysterious Name (불가사의한 이름)**: 무엇을 하는지/담는지 드러내지 못하는 함수, 변수, 타입 이름. → 이름을 바꾼다. 정직한 이름이 떠오르지 않으면 설계가 흐릿한 것이다.
- **Duplicated Code (중복 코드)**: 같은 로직 형태가 변경 안의 여러 hunk나 파일에 나타난다. → 공통 형태를 추출해 양쪽에서 호출한다.
- **Feature Envy (기능 편애)**: 자기 데이터보다 다른 객체의 데이터에 더 많이 손을 뻗는 메서드. → 그 메서드를 탐내는 데이터 쪽으로 옮긴다.
- **Data Clumps (데이터 뭉치)**: 같은 몇 개의 필드나 매개변수가 항상 함께 다닌다(태어나고 싶어 하는 타입). → 하나의 타입으로 묶어 그것을 전달한다.
- **Primitive Obsession (기본형 집착)**: 고유한 타입을 가질 만한 도메인 개념을 기본형이나 문자열이 대신한다. → 그 개념에 작은 전용 타입을 준다.
- **Repeated Switches (반복되는 스위치)**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 곳곳에 반복된다. → 다형성으로 대체하거나 두 곳이 공유하는 맵 하나로 바꾼다.
- **Shotgun Surgery (산탄총 수술)**: 하나의 논리적 변경이 diff 안의 여러 파일에 흩어진 수정을 강요한다. → 함께 바뀌는 것을 한 모듈로 모은다.
- **Divergent Change (뒤엉킨 변경)**: 하나의 파일이나 모듈이 서로 무관한 여러 이유로 수정된다. → 각 모듈이 한 가지 이유로만 바뀌도록 분리한다.
- **Speculative Generality (추측성 일반화)**: 스펙에 없는 필요를 위해 추가된 추상화, 매개변수, 훅. → 삭제한다. 실제 필요가 나타날 때까지 인라인으로 되돌린다.
- **Message Chains (메시지 체인)**: 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색. → 그 탐색을 첫 번째 객체의 메서드 하나 뒤로 숨긴다.
- **Middle Man (중개자)**: 대부분 다른 곳으로 위임만 하는 클래스나 함수. → 제거하고 실제 대상을 직접 호출한다.
- **Refused Bequest (상속 거부)**: 상속받은 것 대부분을 무시하거나 재정의하는 하위 클래스나 구현체. → 상속을 버리고 합성을 사용한다.

### 4. 두 서브 에이전트를 병렬로 생성

두 서브 에이전트 호출을 포그라운드에서 함께 실행하고, 그들이 반환하는 보고서를 취합한다.

**표준 서브 에이전트 프롬프트**에 포함할 것:

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록, **그리고 3단계의 스멜 기준선 전문**(서브 에이전트는 달리 이를 볼 방법이 없다).
- 지시문: "파일/hunk별로 해당되는 곳마다 다음을 보고하라. (a) diff가 문서화된 표준을 위반하는 모든 곳: 해당 표준(파일 + 규칙)을 인용할 것. (b) 발견한 기준선 스멜: 이름을 붙이고 해당 hunk를 인용할 것. 확실한 위반과 판단의 문제를 구분하라. 문서화된 표준 위반은 확실한 위반일 수 있지만 기준선 스멜은 언제나 판단의 문제이며, 문서화된 저장소 표준이 기준선보다 우선한다. 도구가 강제하는 것은 건너뛰어라. 400단어 이내."

**스펙 서브 에이전트 프롬프트**에 포함할 것:

- diff 명령과 커밋 목록.
- 스펙의 경로 또는 가져온 내용.
- 지시문: "다음을 보고하라. (a) 스펙이 요구했으나 누락되었거나 부분적으로만 구현된 요구사항. (b) 요청되지 않은 diff 속 동작(범위 확대). (c) 구현된 것처럼 보이지만 구현이 잘못되어 보이는 요구사항. 각 발견마다 해당 스펙 문장을 인용하라. 400단어 이내."

스펙이 없으면 스펙 서브 에이전트는 건너뛰고 최종 보고서에 그 사실을 적는다.

### 5. 취합

두 보고서를 `## 표준`과 `## 스펙` 제목 아래에 그대로 또는 가볍게 다듬어 제시한다. 두 축은 의도적으로 분리되어 있으므로(_왜 두 축인가_ 참고) 발견 사항을 합치거나 순위를 다시 매기지 **않는다**.

마지막에 한 줄 요약을 붙인다: 축별 총 발견 수와 _각 축 안에서_ 가장 심각한 문제(있다면). 두 축을 통틀어 하나의 최악을 고르지 않는다. 그것이 바로 분리가 막으려는 재순위화다.

## 왜 두 축인가

변경은 한 축을 통과하고 다른 축에서 실패할 수 있다:

- 모든 표준을 따르지만 엉뚱한 것을 구현한 코드 → **표준 통과, 스펙 실패.**
- 이슈가 요구한 것을 정확히 하지만 프로젝트 관례를 깨는 코드 → **스펙 통과, 표준 실패.**

둘을 따로 보고해야 한 축이 다른 축을 가리지 않는다.
